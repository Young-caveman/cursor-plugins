# Pi-compat / T3-contract review of PStack (read-only review)

Verdict: PStack's T3 contract is accurate — every tool name, parameter, and enum it teaches matches the fork's `orchestratorMcp.ts`/`tools.ts`; the real problems are one wrong launch gate, an incomplete `t3_thread_launch` call shape, and unmined capabilities (`task_cancel`, worktree handoff, scheduled-task lifecycle, thread search/queue).
The largest structural leftover is `automations/benny/`, an entire Cursor-only pack that cannot run under T3's four harnesses and is referenced by nothing else; everything else Cursor-flavored is either doctor detection, attribution, or accepted (`make-bot-ui`).
Pi is covered in the README but still absent from the guide, `transcripts.md`, `harness_discovery.py`, and `audit-rollout.py`, and Pi's adapter ignores `interactionMode`, so PStack's "read-only" plan-mode children are instruction-bounded only under Pi.

Scope: `pstack/` (skills, scripts, docs, README, automations, tools) vs `/cave/t3code` @ `yash/swiftui-orchestrator-v2-support` (82caf32396). Reviewed 2026-09-27. No files modified; this report is the only output.

## 1. Compatibility: PStack's T3 usage vs the fork's contract

### 1.1 [medium] `t3_thread_launch` parent gate is stated wrong (and never pre-checked)
- PStack: `skills/setup-pstack/references/t3-delegation.md:15` — "It requires a full-access or default parent".
- T3: `apps/server/src/mcp/toolkits/project/handlers.ts:43-46` — the gate is `caller.runtimeMode !== "full-access" || caller.interactionMode !== "default"` → `capability_denied`; i.e. runtime mode `full-access` **and** interaction mode `default` simultaneously. (Tool description confirms: `apps/server/src/mcp/toolkits/project/tools.ts:91` "Requires a full-access/default caller.")
- Wrong: "full-access or default" reads like either of two runtime modes. If the user's thread is in `plan` mode or a non-`full-access` runtime, every parallel-writer launch in `arena:20`, `swarm:17,21`, `autopilot-full.md:6`, `autopilot-stack.md:5`, `multi-phase-plan.md:72`, `hillclimb.md:12`, `shipping.md:7`, `opening-a-pr.md:5` fails at runtime, and no workflow pre-checks the caller's modes.
- Fix (describe): state the exact gate in `t3-delegation.md`, and make the tool-for-the-job table say: before any `t3_thread_launch`, confirm the parent is `full-access`/`default` (e.g. via `orchestrator_capabilities`' `runtimeMode`/`interactionMode` fields); if not, either ask the user to leave plan mode or fall back to serial single-writer work.

### 1.2 [medium] `t3_thread_launch` call shape is incomplete in the central contract
- PStack: `skills/setup-pstack/references/t3-delegation.md:33` gives only `modelSelection: {instanceId, providerInstanceId→…, model, options}`; `swarm/SKILL.md:21` and `arena/SKILL.md:20,24` likewise mention only `modelSelection`/`workspaceStrategy`. `title` and the task text location are never mentioned.
- T3: `apps/server/src/mcp/toolkits/project/tools.ts:94` `title: TrimmedNonEmptyString` is **required**; `tools.ts:104` `message` is optional and `apps/server/src/mcp/toolkits/project/handlers.ts:66-77` omits `initialMessage` entirely when `message` is undefined → the launch creates an **idle thread that never starts work**. T3's own instructions say "Put the task in `message`, not `prompt`" (`apps/server/src/provider/T3OrchestrationInstructions.ts:15`).
- Wrong: an agent that reuses `delegate_task`'s parameter names (`task`/`prompt`) silently produces an idle thread and then "waits" on it forever via `t3_thread_wait` (which returns immediately for an idle thread).
- Fix: give the full call shape in `t3-delegation.md`: `{title, message: <the brief>, modelSelection, workspaceStrategy, interactionMode}` and warn that omitting `message` creates an idle thread.

### 1.3 [low] `includeSubagents` semantics inverted in transcripts doc
- PStack: `skills/setup-pstack/references/transcripts.md:8` — "`t3_thread_list` (newest first; `includeSubagents` for delegated children)" implies you must pass it to see children.
- T3: `apps/server/src/mcp/OrchestratorMcpService.ts:1712-1715` — `includeSubagents: input.includeSubagents !== false`; children are included **by default**, the flag excludes them. Param name itself is correct (`packages/contracts/src/orchestratorMcp.ts:287`).
- Fix: reword to "delegated children are included by default; pass `includeSubagents: false` to hide them".

### 1.4 [low] plan-mode hedge can now be specific: Pi has no plan enforcement
- PStack: `skills/setup-pstack/references/t3-delegation.md:47` — "Plan mode's enforcement differs by provider and has not been verified per provider." (`why/SKILL.md:80` similarly.)
- T3: `interactionMode: "plan"` maps to each provider's native plan mode in `ClaudeAdapterV2.ts:1325`, `CodexAdapterV2.ts:715`, `OpenCodeAdapterV2.ts:3333`, `CursorAdapterV2.ts:324`, `AcpAdapterV2.ts:5910` — but `PiAdapterV2.ts` contains **zero** `interactionMode` handling (grep of the adapter: only `runtimePolicy.cwd`/`runtimeMode` are consumed, lines 405, 434). A Pi child with `interactionMode: "plan"` is prompt-bounded only ("do not edit files" in the brief).
- Fix: upgrade the hedge to: verified for Claude/Codex/OpenCode/ACP/Cursor; **not enforced at all by the Pi adapter** (this fork revision), so brief wording is the only guard there. Relevant to `interrogate:38`, `how:22`, `arena:34`, `swarm:21`, `show-me-your-work:67`, `maintain-verification-skill:29`.

### 1.5 [low] "activity view includes tool calls" is plausible but unproven

## 2. Capabilities PStack clearly should use but does not

Census: no occurrence anywhere in `pstack/` (excluding `develop-log/`) of `task_cancel`, `t3_thread_interrupt`, `t3_thread_fork`, `t3_thread_merge_back`, `t3_queue_*`, `t3_pending_request_*`, `t3_worktree_*`, `t3_thread_search`, `t3_thread_organize`, `link_pull_request`, `update_scheduled_task`, `delete_scheduled_task`, `run_scheduled_task_now`, `preview_*`, `device_*`. Used: `orchestrator_capabilities`, `delegate_task`, `task_status`, `t3_thread_launch`, `t3_thread_wait`, `t3_thread_read`, `t3_thread_list`, `t3_thread_send` (orchestrate only), `schedule_task`, `create_threads` (named once, negatively).

1. [medium-high] `task_cancel` (and `t3_thread_interrupt`). `pause-safely.md:5` says "cancel any nested subagents" with no mechanism, and `autopilot-full.md:10` / `autopilot-stack.md:6` / `multi-phase-plan.md:43` order "Stand it down and dispatch a replacement at once" for stuck lanes. Without `task_cancel` the child keeps burning tokens; without `t3_thread_interrupt` a launched writer keeps committing to its worktree after being "stood down". T3 evidence: `orchestrator/tools.ts:82-92`, `225-235`. Fix: add a "stop work" row to `t3-delegation.md`'s tool table (`task_cancel` for delegated tasks, `t3_thread_interrupt` for launched threads) and name it in pause-safely and the stand-down instructions.
2. [medium-high] `t3_worktree_status` + `t3_worktree_handoff`. `opening-a-pr.md:5` ("Work from a git worktree off main…") and the guide's overnight contract (`docs/guide/07-overnight.md:12,22`, `docs/guide/02-poteto-mode.md:71`) tell the *calling* agent to work from a fresh worktree, but plain `git worktree add` + `cd` "does not update the thread binding" (T3's own warning, `T3OrchestrationInstructions.ts:23`); `t3_worktree_handoff` is the supported move (`worktree/tools.ts:21-33`, including `continuationPrompt`). Fix: opening-a-pr and any "work in a fresh worktree" instruction should use `t3_worktree_status` first and `t3_worktree_handoff` for the calling thread (workers still get `t3_thread_launch`).
3. [medium] Scheduled-task lifecycle: `update_scheduled_task` / `delete_scheduled_task` / `run_scheduled_task_now`. Four playbooks arm `schedule_task` and then say "Disable the scheduled task when the program ends" (`autopilot-full.md:10`, `autopilot-stack.md:6`, `multi-phase-plan.md:42`, `babysit.md:12`) without naming any tool that can do it. Fix: name `update_scheduled_task` (enabled=false) / `delete_scheduled_task`, and `run_scheduled_task_now` for "run this audit tick now". (`orchestrator/tools.ts:107-142`, `thread/tools.ts:236`.)
4. [medium] `t3_thread_search`. `recall/SKILL.md:19` ("grep the topic first and then read only the matching chats"), `automate-me`, `reflect` mine history via `t3_thread_list` + full reads. `t3_thread_search` searches thread titles *and content* in the project (`thread/tools.ts:225-234`). Fix: transcripts.md's "Other threads" bullet should search first, then read.
5. [medium] `t3_queue_list/read/edit/cancel/promote_to_steer`. `orchestrate.md:25` appends standing orders mid-run ("Paste it verbatim into every spawn and every resume") and `orchestrate.md:95` bans messaging liveness checks. The queue tools make messaging safe and precise: inspect what is queued at an idle worker (`t3_queue_list`), edit/cancel a stale instruction, or steer a correction into an active run (`t3_queue_promote_to_steer`) when a standing order changes under a running lane. Fix: orchestrate's messaging section should specify `t3_thread_send` with `mode: "queue"`/`"steer"` and the queue tools; never `restart`/auto-start for liveness.
6. [low-medium] `t3_pending_request_list/read/respond`. The audit tick judges lanes by side effects and treats silence as stuck (`autopilot-full.md:10`); a lane blocked on a T3 user-input question looks stuck but is answerable from the coordinator (consistent with **principle-never-block-on-the-human**). Fix: drain step checks pending requests on each lane before declaring it stuck.
7. [low-medium] Incremental text recovery (`itemId`/`textOffset`/`nextTextOffset`). `transcripts.md` and `show-me-your-work:56` read long transcripts via `t3_thread_read`, but items are truncated at 20,000 chars by default (`OrchestratorMcpService.ts:87`) and PStack never mentions the continuation fields (`orchestratorMcp.ts:325-330`). Fix: one line in transcripts.md: when `textTruncated`, continue with `itemId` + `textOffset=nextTextOffset`.
8. [low-medium] `link_pull_request`. `opening-a-pr.md:33`, `shipping.md:7`, `autopilot-*` track PRs purely through `gh`/`origin`. `link_pull_request` registers the PR on the thread so T3 tracks host status and settles the thread on merge (`pullRequests/tools.ts:188`). Fix: opening-a-pr step "return the URL" should also call `link_pull_request`.
9. [low] `preview_*` / `device_*`. `multi-phase-plan.md:124` demands a 30-60s review video "when the verification surface supports capture" and `visual-parity.md:8` wants image diffs; T3 has `preview_recording_start/stop`, `preview_snapshot`, `device_screenshot` (`preview/tools.ts`, `device/tools.ts`). Fix: one sentence in create-verification-skill's capture section pointing at these when the surface is the T3 browser or a simulator.
10. [low] `t3_thread_fork`/`t3_thread_merge_back` — only a maybe: `session-pickup.md:5` reconstructs state by reading an old trail; forking that thread from `{type:"latest_stable"}` (`thread/tools.ts:187-205`) resumes with native context. Note the philosophical conflict: PStack briefs "stand alone" and deliberately copy no history, so fork's context inheritance cuts against the grain. `create_threads` has no concrete PStack use (delegate_task covers read-only fan-out) — correctly unused.

## 5. Conflicts with T3's injected instructions (`T3OrchestrationInstructions.ts`)

1. [medium] Native subagents. T3: "Prefer the current provider's native subagent tools for same-provider parallel work when available" (`T3OrchestrationInstructions.ts:9`, repeated in the `delegate_task` tool description `orchestrator/tools.ts:58`). PStack: "Don't use native subagents even for same-provider work, because they bypass the pool's model and options" (`t3-delegation.md:5`). PStack's override is deliberate and stated ("these rules replace T3's general delegation advice"), but the losing rule is re-shown inside the `delegate_task` tool description at the moment of choice, and in Claude Code a native subagent tool is always "available", so a model can rationalize past the skill. Fix: put one explicit sentence in each spawning step ("call `delegate_task` even when the harness offers its own subagent tool") so the decision point carries the override, not just the reference doc.
2. [medium-high] `t3_thread_launch` permission. T3: "Use them only when the user explicitly asks for separate/new/top-level threads or conversations. **Never use them merely because** the user said 'subagent' or **requested parallel delegated work**" (`T3OrchestrationInstructions.ts:10`; same in `project/tools.ts:91`). PStack: "A workflow the user started that needs parallel writers counts as the user's request for new threads" (`t3-delegation.md:5`) and instructs unconditional launches in `arena:20`, `swarm:17`, `autopilot-*`, `shipping.md:7`, `hillclimb.md:12`. A model obeying the injected rule literally will refuse the writer path of arena/swarm/autopilot (the user asked for an arena, not for threads). Fix: at Frame time, tell the user "this opens N worktree threads" and record their go-ahead as the explicit request; state in `t3-delegation.md` that this sentence is the sanctioned interpretation and how to obtain the explicit request.
